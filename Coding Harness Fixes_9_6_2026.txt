**A failed shell command destroys all staged progress, not just its own effect**


`executor/tools/bash.py`:
```python
rolled_back = process.returncode != 0
if rolled_back:
    rollback_mutation(root, checkpoint_id)
```
Any non-zero exit code triggers a full rollback of the mutation checkpoint taken immediately before the command ran — unconditionally, regardless of whether the command was expected to mutate anything, and regardless of whether it made real, useful progress before failing partway through. A code generator that writes three files and then exits 1 on a fourth loses all three. A linter or test runner that legitimately exits non-zero (that's its whole job) doesn't lose anything only because it isn't classified as a mutation — but anything that both mutates *and* can fail (codegen, migrations, `make`, scaffolding scripts) is caught by this.

**Why it matters most:** this actively destroys work rather than merely limiting capability. It's also silent in the sense that the agent has to infer from `rolled_back: true` in the tool result that its prior progress is gone, rather than the harness distinguishing "command failed" from "your mutation transaction was discarded."

**Implementation idea:** the harness already computes and returns whether output was truncated, so extending the same result payload to separate "process exit code" from "checkpoint outcome" is a small change. Concretely: only roll back if the command's *own* declared intent was mutation-free (e.g., known-read-only commands like `pytest`, `ruff check`, `grep`) — or, more conservatively and more consistent with the existing security posture, keep rollback-on-failure as the *default* but let the tool call opt out per-invocation (e.g. `rollback_on_failure: false`) for commands the agent knows are expected to fail-but-progress, with the checkpoint diff still surfaced either way so the agent can decide whether to keep or discard.
